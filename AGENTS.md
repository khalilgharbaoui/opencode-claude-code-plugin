## Project Shape

- This is an npm package that exposes an opencode provider by wrapping the Claude Code CLI (`claude`), not the Anthropic HTTP API directly.
- Package entrypoint is `src/index.ts`; runtime provider behavior lives mostly in `src/claude-code-language-model.ts`, which now holds the `ClaudeCodeLanguageModel` class and little else. Its free-standing pieces moved out verbatim and it re-exports every symbol tests and `src/index.ts` used to import from it, so an old import path still resolves: `src/prompts.ts` (appended system prompt text and `buildAppendedSystemPrompt`), `src/auto-continue.ts` (the continue-or-stop decision), `src/ask-user-question.ts` (`AskUserQuestion` rendering and its deny message), `src/fast-mode.ts` (`reportFastModeState`), `src/call-options.ts` (session affinity, opencode agent, compaction model, `hasNewUserContent`), `src/proxy-results.ts` (reading opencode's answer back out of the next prompt), `src/control-request.ts` (`can_use_tool` allow/deny), `src/spawn-planning.ts` (proxy defs, MCP config, live tool registry, skill-bridge and plan-mode gates, the proxy server), `src/title.ts` and `src/usage.ts`. **There is one turn implementation, `doStreamForHost`, and the state its handlers shared is an object now, not a scope.** `src/turn-state.ts` holds `TurnState` and `createTurnState`, one per turn, with a comment on each field naming the invariant that owns it; `src/turn-controller.ts` holds the two watchdogs, late-result delivery, the batched drain, both tool-call finishes and the auto-continue nudge; `src/stream-parser.ts` holds the CLI line handler (`createLineHandler`) and `StreamParserContext`, the twelve prologue values it reads; `src/turn-abort.ts` holds `watchTurnAbort`, the one thing that observes this turn's abort signal, created before the prologue's first await (h #g182). What stayed in `doStreamForHost` is what also reads that prologue: the spawn block, `completeResult`, the close handler, `cleanupTurn`, the proc-error handler and the abort branch. Behaviour-preserving: no log line, stream part or session-manager call changed, and a paired live probe matched line kind for line kind. (h #g165) `doGenerate`'s duplicate copy of that parser is gone (0.29.x): `doGenerate` is `doGenerateViaStream`, which aggregates `doStream`'s parts, and the only thing that differs between the two entry points is `TurnMode`, which suppresses the account-failover dialog on a `doGenerate` turn. Measured on opencode 1.18.32: nothing there calls `doGenerate` at all, not even a title request. `test/do-generate.test.ts`. (h #g164)
- `src/message-builder.ts` owns AI-SDK prompt to Claude CLI stream-json message conversion, including `/compact` transcript rendering.
- `src/session-manager.ts` owns Claude CLI process reuse, session ids, LRU eviction, and CLI arg construction.
- `src/session-fork.ts` decides whether a new opencode session is a fork of one this provider already served, by matching conversation content rather than any host id. Pure, injected rather than importing the session manager, and only ever consulted on a turn that was about to replay. (h #g187)
- `src/session-resume-store.ts` keeps, across opencode restarts, which Claude session answered each session key, with the fork module's digest chain of the conversation it answered. The only file the plugin writes under `$XDG_STATE_HOME` besides `cleanup-stale.json`. (h #g197)
- `src/cli-version.ts` gates optional CLI flags. Do not pass newly-added Claude CLI flags unconditionally. **A probe our own 5-second deadline killed is the one failure that is NOT cached, up to `MAX_DEADLINE_REPROBES` (2) consecutive times per probe key** (`killedByDeadline`, `forgetDeadlineKill`; the third kill is cached with one WARN, because a `claude` or wrapper that is always slower than the deadline would otherwise make every turn wait the full deadline; an answer resets the count): it describes the machine, not the binary, and caching it withheld every version-gated flag, the skill bridge and `/btw` from the whole opencode process after one busy turn. Everything else (missing binary, non-zero exit, unparseable output) stays cached, so a broken binary is still one spawn. Do not raise the deadline instead: it bounds how long a wedged `claude` holds the first turn. `test/cli-probe-cache.test.ts`. (h #g181)
- `src/plan-usage.ts` runs the CLI's own free `/cost` command for `/claude-code-doctor usage`, and is the only place the plugin invokes a CLI slash command. Nothing on a turn path may import it. (h #g167)
- `src/stale-build.ts` answers one question nothing else in opencode can: is the build this process is RUNNING still the build on disk? It records the loaded version, entry path, mtime and size at module load, and a throttled check re-reads them. Pure apart from `fs`, injectable through `createStaleBuildWatch`, and the only module that may call `pluginVersion()` for a comparison. (h #g192)
- `src/tui-log-sink.ts` is the only thing that knows opencode's `app.log` and `tui.showToast` routes. It builds the `LogSink` `src/logger.ts` uses when a full-screen TUI owns the terminal, and is imported from the V1 entry only. Pure apart from those two calls, and it must never import anything that logs. (h #g193)
- `src/diagnostic-bundle.ts` is the allowlist redactor behind `/claude-code-doctor bundle`; `src/log-messages.ts` is its generated set of plugin-authored NOTICE/WARN/ERROR message literals, and `src/log-message-scan.ts` is the extractor that produces it. **`log-message-scan.ts` reads `src/` off disk, so nothing on a turn path may import it**: only `scripts/generate-log-messages.ts` and `test/diagnostic-bundle.test.ts` do. (h #g183)
- `src/claude-session-bun.ts` + `src/claude-session-wrapper.ts` own the experimental interactive transport (PR #10): the interactive `claude` TUI under Bun's native PTY, prompts typed via bracketed paste, output tailed from the session JSONL transcript. Opt-in via `interactive: true` / `CLAUDE_CODE_INTERACTIVE_TRANSPORT=1`; headless `--print` stays the default.
- **One package serves opencode 1.x and 2.x.** The default export carries both `server` (1.x) and `setup` (2.x). `src/v2.ts` is the 2.x entrypoint, `src/opencode-v2-types.ts` a hand-written mirror of the 2.x API slice, `src/v2-client.ts` answers live-state calls in 1.x shapes, `src/host-tools.ts` renames tool calls into 2.x's vocabulary. See `V2.md`.
- Build output is `dist/`, is gitignored, and is rebuilt by CI. Do not commit `dist/`.
- **The runtime dependencies are `@ai-sdk/provider` and `jsonc-parser`, and nothing else. Do not re-add `@ai-sdk/provider-utils` for `generateId`** (`src/ids.ts` is the local one, same 16-character `[0-9A-Za-z]` shape): it was the only thing the plugin used from it, and its AI SDK v5 line (`^3.0.8`, beside the v6 `@ai-sdk/provider ^3`) pulled `undici ^5.29.0` into every install, which `npm audit` flagged with thirteen advisories (three high), plus a second `@ai-sdk/provider` and a `zod` peer. **`npm audit` needs a lockfile and this repo keeps none**, so audit a scratch copy: `npm i --package-lock-only --ignore-scripts`, then `npm audit --omit=dev` for what users install. The one remaining finding is dev-only `esbuild` under `tsup` (its Windows dev server, which nothing here runs), left until `tsup` widens its `^0.27` range. `test/ids.test.ts`. (h #g186)

## Release Workflow

- Never run `npm publish` manually. Tag push triggers `.github/workflows/publish.yml`, which publishes to npm.
- Publishing uses npm **trusted publishing (OIDC)**, not a token (since v0.6.2): `id-token: write`, npm >= 11.5.1, `npm publish --access public` with **no `NODE_AUTH_TOKEN`**. The trusted publisher must match the repo and workflow filename `publish.yml`; the legacy `NPM_TOKEN` secret is unused. If a publish fails on auth, check that config, not a token. (h #g17)
- Release flow: commit code/docs, then `npm version patch` (or minor/major), then `git push origin master --follow-tags`. Prior tag messages are `v0.x.y`, keep that style, and confirm with `gh run list --limit 3`.
- **Verify a publish from the `Publish package` step's own tail (`+ <pkg>@<version>`) and cross-check the version document's `shasum` against its `npm notice shasum:` line; the version document can lag the publish by several minutes (about seven on 2026-10-01), so poll for ten before concluding anything. Never judge a release by the package document, `npm view` or an install from the maintainer's Mac**, where Aikido's minimum-package-age filter hides fresh versions. Read Aikido's event log before calling anything a registry fault. A real auth failure fails the step with a 404 on the PUT. (h #g21)
- GitHub Releases lapsed after v0.9.2 and are optional. Write notes for anything security-relevant or behaviour-changing. (h #g22)
- A freshly published version will NOT appear in a local opencode until `rm -rf ~/.cache/opencode/packages/@khalilgharbaoui/opencode-claude-code-plugin@latest` plus a full relaunch; a plain restart never re-resolves `@latest`. (h #g23)
- Do not add a Claude co-author trailer to commits.
- Keep the `docs/` pages updated when adding public options, env vars, required CLI versions, or behavior users can observe; `README.md` is the landing page and changes only when its own copy stops being true. See the docs rule under Commands. (h #g188)

## High-Signal Runtime Gotchas

### Aborts, deadlines and process lifetime

- **The run-state read that decides whether an abort at a tool boundary is real must ask for the session's own directory.** opencode keeps one status map per workspace directory and the plugin's client is scoped to whichever directory loaded it last, so asked without a directory a session running in any other workspace is absent from the map and reads `idle`: every abort at a tool boundary then rejected the parked call (`Provider stream was aborted while opencode was running its proxy tool calls`) and interrupted the CLI, which the model reported as the user interrupting it. Measured 2026-10-05 on 1.18.32: five sessions busy, each in its own workspace, the unscoped map empty and each per-directory map showing them busy; 111 such rejections in two and a half days of one machine's CLI transcripts, hitting long tool calls (VM ssh) in seats that run in their own workspace. `fetchSessionRunState(sessionID, directory?)` looks the directory up with `fetchSessionDirectory` when not given one, `settleSessionRunState` once per window, and the release now logs the state it read. `test/runtime-status-sessions.test.ts`, `test/process-lifecycle.test.ts`.
- **A tool-result turn resolves the parked proxy calls and writes no user envelope, so user messages the host promoted beside those results must be forwarded or the CLI never sees them.** opencode records a background-PTY notice, a mail-watch notice or a steered prompt as delivered when it promotes it at the step boundary, and the next prompt carries it after the tool result; the matched-results branch returned without writing it (measured 2026-10-05 against a live server: the Claude CLI transcript held none of six notices recorded by opencode, and held all six as `queued_command` attachments once forwarded). `getTrailingUserMessages` returns the plain user messages after the last assistant message, and `ActiveProcess.forwardedUserMessages` (assistant index and count) stops a later tool-result turn for the same boundary sending them twice. Judge delivery by the CLI transcript, not opencode's history: a mid-turn stdin message appears there as `queue-operation` plus a `queued_command` attachment, not as a `user` row. On the interactive transport a stdin write is a new TUI turn that would supersede the one parked in the proxy call (h #g204), so the message is typed into that turn's own input queue instead (`interactiveControl.queueInput`, h #g206): measured on 2.1.288, text submitted while a tool call runs is recorded as `queue-operation` enqueue/remove plus a `queued_command` attachment and answered in the same turn, which ends once. Only while the TUI turn runs, never into a parked plan dialog, confirmed by the enqueue record before the call is resolved. Live, both majors and both transports, A/B against v0.42.0 (which dropped it). `test/forward-user-content.test.ts`, `test/interactive-pty.test.ts`.
- **An abort at a proxy tool boundary is usually opencode, not the operator**: 1.18.32 aborts every step ending in tool calls, and `AbortSignal.reason` is identical either way. Only a positive `busy` from `settleSessionRunState` keeps the pending calls; `unknown` releases. `test/process-lifecycle.test.ts`. (h #g26)
- **An abort that lands while a turn is being PREPARED must stop it, and the only thing that can see it is a watch created before the prologue's first await** (`watchTurnAbort`, `src/turn-abort.ts`): `addEventListener("abort")` on a signal that already aborted never fires, so the stream's own handler, which cannot exist until the prologue has finished, missed every stop in that window and the turn spawned, wrote and billed anyway (measured: a turn alive at 5,874 ms against a 5,000 ms signal). The handler is registered through `onAbort` in the **synchronous** part of `start()` now, never inside `setup()`, and `TurnState.cliAskedForWork` (set at exactly two places, the envelope write and the top of the tool-result branch) selects a new FIRST branch in front of the existing ones: close the stream, discard a proxy MCP server this turn created but never handed to a child, send **no** `interrupt` (a reused process's last turn is not this doStream's to stop) and leave an earlier step's pending proxy calls untouched, so #g26 and #g82 still own how they end. Three prologue checks, plus `stoppedBeforeWork()` on entry to `setup()`, at both spawn sites and after `interruptTurn`. **The raced `detectCliVersion` is left running on purpose**, because its answer is cached process-wide and cancelling it would be #g181 again; only the MCP connect wait takes the signal (`getRuntimeMcpStatus({ signal })`), because its poll loop is ours. `test/prologue-abort.test.ts`. (h #g182)
- **A proxy deadline must not count the operator's time on a permission prompt.** Both timers go through `armProxyDeadline` and its `ProxyDeadlineGuard`; `isProxyCallStillServed` keeps a call only when `emitted` **and** the session reads `busy`, rechecking every `PROXY_DEADLINE_RECHECK_MS`. No guard, a throwing guard or `unknown` end it as before. `test/broker.test.ts`. (h #g27)
- **Abort sends the CLI an `interrupt` control request** (`interruptTurn`), or the turn runs on and bills. `noteTurnStarted` marks in flight at every stdin write asking for work, and the terminal `result` clears it inside the `rl` handler, **never** a permanent `lineEmitter` listener. `test/session-manager.test.ts`. (h #g59)
- **`idleProcessTimeoutMs` is off unless set** (`resolveIdleProcessTimeoutMs`, so unset and `0` both arm nothing). Unref'd, cancelled by every get/set/detach/spawn/exit, deleting only the same process object; a process found `turnInFlight` is re-armed, never killed. `test/session-manager.test.ts`. (h #g60)
- **The child's stdin needs its own `error` listener, and `proc.on("error")` is not it**: an `error` on a listener-less stream throws inside **opencode's** process. `spawnClaudeProcess` attaches one, logs at WARN, calls `settleTurn`, and deliberately does not end the turn. `test/session-manager.test.ts`. (h #g61)
- **LRU eviction must never take a process that is mid-turn**: `evictIfNeeded` walks insertion order for the first with `turnInFlight !== true`, and when all are busy evicts **nothing** and warns. Do not "restore" the one-liner. Cap is **16**, and idle eviction stays off unless `idleProcessTimeoutMs` is set, so the cap is the only bound on a default install. `test/session-manager.test.ts`. (h #g62, #g179)
- **A deleted opencode session releases everything at once, and host exit kills what is left.** The `event` hook acts on `session.deleted` only (`extractDeletedSessionId`); `deleteActiveProcessesForSession` also drops session id, plan-mode questions, ledger and summary, never matching the `"default"` bucket. `test/process-lifecycle.test.ts`. (h #g63)
- **A child that closes without a `result` is an error, not a `stop`**: emit an `error` part plus `finishReason: "error"` from `describeChildCrash(exitCode, signal, lastStderr)`. `retainStderr` keeps a 2 KB tail, the branch waits `CHILD_EXIT_STATUS_GRACE_MS` for `exit`, and an abort is exempt. `test/respawn.test.ts`. (h #g64)
- **Reused-process start watchdog** (`src/turn-controller.ts`): `armStartWatchdog(state)` fires only on the fresh-turn write path, which the inactivity watchdog ignores. First fire (`CLAUDE_CODE_START_WATCHDOG_MS`, 90 s) calls `respawnActiveProcess`, reusing the proxy server, prompt file and mcp hash and appending `--resume`. `test/respawn.test.ts`. (h #g84)

### The proxy

- **proxy-mcp `tools/call` responses MUST be MCP results (`{ result: { content, isError } }`), never JSON-RPC error envelopes**, which the CLI rejects as malformed. All three error paths return `isError: true`; `requestId`/`requestMethod` are hoisted above the try, so do not regress to `id: null`. `test/proxy-mcp.test.ts`. (h #g78)
- **The proxy MCP server answers `initialize` from a fixed object and must never start validating the client's `params`.** That is what makes it immune to the CLI's capability negotiation: 2.1.287 began sending `elicitation: {form:{}, url:{}}` in its client capabilities (the code is already in 2.1.286) and offers `bareElicitationCapability` as an opt-out for servers that reject an unknown field there, which is a *server* problem the plugin's server cannot have. A bridged server that rejects it gets one automatic retry from the CLI without elicitation, and a server that still fails lands in `mcp_server_errors` (h #g167). `PROTOCOL_VERSION` stays `2024-11-05`. (h #g191)
- **The proxy MCP endpoint is authenticated** (GHSA-3mxm-w7gf-3c5x, 0.13.2): a 256-bit bearer token in the `0600` `--mcp-config`, plus four guards **before** `readBody`: `Host` equals the bound authority, `Origin` absent, `Content-Type` is `application/json`, bearer matches under `timingSafeEqual`. Never log `authToken`. **Upgrading does not patch a running opencode.** `test/proxy-mcp.test.ts`. (h #g79)
- **Proxy call deadlines are per-tool, not flat.** `resolveProxyCallTimeoutMs(toolName, input, overrides)` is the single resolver for BOTH the HTTP handler and the broker, so any new timeout site must call it. Layers: 10-min default, per-tool default (`task`/`task_batch` **none**, `question` 30 min), `proxyToolTimeoutMs`, then for `bash` only `max(resolved, input.timeout)`. (h #g83)
- **A deadline of 0 means no timer, and the MCP client ceiling follows the largest deadline.** Both layers guard their timer on `deadlineMs > 0`. `resolveProxyClientCeilingMs` writes the `timeout` into Claude's `--mcp-config` (without one, Claude's HTTP MCP client gives up at 60 s) and is `MAX_PROXY_TIMEOUT_MS` whenever any tool has no deadline, because the CLI rejects `timeout: 0`. `TASK_PROXY_NOTE` must describe the real deadline (none by default; a positive `proxyToolTimeoutMs` adds one) and background mode. (h #g83)
  - **A deadline of 0 means no timer**: both sites guard `setTimeout` on `deadlineMs > 0`. Keep `buildProxyTimeoutError`'s `"timed out after"` + `"waiting for opencode to resolve"` and the `task` "do not schedule a wake-up" note. Do not reintroduce the flat `PROXY_CALL_TIMEOUT_MS`. `test/broker.test.ts`.
- **A proxied call ends on an event, not on a clock**: the result, an abort, the next message's orphan sweep, the child dying, a deleted session or host exit; a hung-up CLI or respawn keeps the entry for late-result recovery. **Every terminal-event test asserts both registries.** `test/proxy-task.test.ts`. (h #g82)
- **A call with no deadline reports itself, because nothing else will** (`PROXY_STALL_WARNING_MS`, 5 min, repeating); it **never ends a call**. Armed only at `PROXY_NO_DEADLINE_MS`, WARN, `unref`'d, removed via `clearPendingTimers(pending)` because a call holds **two** timers. `test/broker.test.ts`. (h #g81)
- **Proxy recovery (0.15.0)**: SSE replies flush headers at once plus keepalive comments, and JSON-only clients get the same via `openJsonStream`. Only broker-backed calls stream, and nothing flushes before the four guards ran. `pendingProxyCompletions` must be consumed once at both terminal boundaries and preserved across respawn (`deliverPendingCompletions`, `src/turn-controller.ts`). `test/proxy-task.test.ts`. (h #g119)
- Two forks measured the ~300 s proxy wall as undici's `headersTimeout`/`bodyTimeout` plus a 300 s MCP-idle timer; the 0.15.0 fix covers it. Do not claim a specific timer without fresh evidence. (h #g68)
- **Do not wait for `message_stop` to drain proxy calls**: it deadlocked two ordinary Bash calls, because the CLI blocks inside the MCP call before emitting it. Our broker drains as calls arrive. (h #g69)
- **`proxyOpencodeMcpTools` is off by default, and MCP tools are discoverable only from `doStream`'s `tools` argument**: they join the model tool set after `ToolRegistry` is enumerated, so `client.tool.list()` never sees them. **Pair it with `strictMcpConfig: true`**, or the CLI calls the server directly. `test/proxy-mcp.test.ts`. (h #g80)
  - `resolveMcpProxyToolDefs` does the `<server>` / `<server>_<tool>` prefix match, and `excludeServers` covers only servers a def was built for, so an unmatched server is never stranded. The bridged config file is content-addressed **over the file body, not over `hash`**.
  - **`--mcp-config <configs...>` is variadic**: push the flag once followed by every path, never a repeated flag, and parse every argument until the next option.
  - `proxyOpencodeTools` (PR #38) needs an explicit allowlist keyed on registry ids, because a plugin-declared tool belongs to no MCP server and no prefix rule reaches it.

### Tools and streaming

- **A CLI-executed tool's `tool-result` must carry the same mapped name as its `tool-call`** (`toolCallsById` stores `mappedName`, both set sites): opencode pairs tool parts by name, and opencode 2.0.16 aborts the turn on a mismatch ("Tool result name changed"), which broke every Claude-side MCP server call until PR #46 (@acastro2). `test/mcp-tool-result-name.test.ts`.
- **Every CLI-executed `tool-call` part goes out through `emitCliToolCall` (`src/turn-state.ts`), once per id, and whichever frame needs it first wins.** `tool-input-start` is emitted at `content_block_start`, and the matching `tool-call` used to be emitted only at `content_block_stop`, which is too late for two measured frames: the CLI's own `tool_result` (it precedes the block's close for a tool the CLI **refuses**, measured verbatim on 2.1.286 with `--disallowedTools Write`) and the end of a step that waits on a proxied call (the CLI answers one assistant message's tool calls with ONE `user` frame, so it withholds its own results until the proxied one is answered, which cannot happen before the step ends). Either way the row never got a result: opencode 2.0.22 reports `Provider did not return a tool result` and 1.18.34 leaves it pending. So `adoptOpenCliToolCall` registers an open block from the result handler, and `closeDeferredCliToolResults` closes the rest out in `finishWithToolCalls` with `CLI_RESULT_DEFERRED_OUTPUT`, which must stay a non-error: nothing failed, the output is in Claude's own context. Waiting is not an option and `finishWithQuestionCall` does not need this. `test/deferred-cli-tool-result.test.ts`, `test/mcp-tool-result-name.test.ts`. (h #g190)
- `signature_delta` is expected encrypted thinking metadata. Ignore it quietly; do not treat it as an error.
- `WebSearch` with the default `"claude"` routing must NOT be forwarded as a tool-call part, because opencode has no registry entry and the AI SDK rejects unknown tool names. `mapTool` returns `skip: true` and the sites render a `> **Web search:** …` line; explicit `webSearch: "<tool>"` still forwards. `test/tool-mapping.test.ts`. (h #g72)
- `tool-input-delta` parts must only be forwarded when `tool-input-start` was actually emitted, or opencode creates a permanently-pending `⚙ unknown` part. Gate on `started`, but keep accumulating `inputJson` unconditionally: the skip-path text rendering depends on it. (h #g73)
- **`toolCallMap` (now on `TurnState`, read in `src/stream-parser.ts`) is keyed by content-block index and MUST be deleted at `content_block_stop`**: indices restart per assistant message, so a stale entry re-emits a completed `tool-call`, opencode aborts the part, and the `task` tool reports `Subagent failed`. Do not "tidy" the delete away. `test/tool-block-index.test.ts`. (h #g76)
- Claude CLI emits internal tools (`Agent`, `ToolSearch`, `AskFollowupQuestion`, `TaskList`, `TaskGet`, `TaskStop`) with no opencode entry; they live in `CLAUDE_INTERNAL_TOOLS` and must be skipped, or they surface as `⚙ invalid`. `TaskOutput` is the exception (a `bash echo`).
- **Subagent dispatch must be steered at the tool *and* the prompt**, or the model calls the CLI's `TaskCreate` todo tool and narrates a dispatch that never ran: `overlayTaskProxyDescription` front-loads opencode's live agent-type list, and `SUBAGENT_DISPATCH_HINT` names `mcp__opencode_proxy__task` as the only dispatch path. `test/subagent-hint.test.ts`. (h #g74)

(h #g184, #g185)
- **`tool_use_summary`, `prompt_suggestion` and `command_lifecycle` are deliberately ignored, each for a measured reason, and none of them is reachable by accident.** `tool_use_summary` needs `CLAUDE_CODE_EMIT_TOOL_USE_SUMMARIES` in the env and costs a model call per tool batch to narrate tool rows opencode already renders. `prompt_suggestion` needs `--prompt-suggestions` plus a turn-origin check and a server-side gate, and produced zero frames even with the flag on; it would also be putting words in the operator's mouth. `command_lifecycle` needs a `uuid` on the inbound envelope, which `src/message-builder.ts` does not write, so the CLI's own schema says it can never fire here (confirmed both ways: zero without, `queued`/`started`/`completed` with). Being in the CLI's SDK allowlist is necessary and nowhere near sufficient. Do not re-derive these without re-running the probes in the history entry. (h #g184)
- **`system`/`status`, `thinking_tokens`, `task_started` and `task_notification` DO all arrive in the plugin's mode, and all four are deliberately unparsed.** Measured live on 2.1.286 and 2.1.280 (`status` and `thinking_tokens` on an ordinary turn; the task pair needs a CLI-side background task, which a default `proxyTools` prevents). `status` is `"requesting"` / `"compacting"` and says only what the plugin just did; `thinking_tokens` is explicitly "approximate progress for spinners/pills, not the authoritative billed output_tokens", so adding it to any tally would double-count (the real number is `usage.output_tokens_details.thinking_tokens`); the task pair's one plugin-visible hazard is fixed at the replay instead (h #g189). 2.1.286 also adds ten `system` subtypes over 2.1.280, seven of them `ui_*` for the fullscreen surface, plus `per_turn_effort_changed`, `session_metadata` and `session_title_changed`: none is parsed either, and `init` gained `per_turn_effort_active`. (h #g191)
- **A proxied tool costs one extra CLI API call per process, it is a `ToolSearch`, and that is inherent.** Claude Code defers MCP tools behind `ToolSearch`, so the model spends a request finding a proxied tool before calling it; built-ins are never deferred. Measured on 2.1.280: 3 API calls proxied against 2 unproxied for one `echo`, amortising to 4 against 3 for two calls (one `ToolSearch` either way), unchanged at 28 tools. **There is no post-tool "digest" turn in this architecture**, so do not port that claim from Meridian. `ENABLE_TOOL_SEARCH=0` removes the call and measured 2.5 to 4 times the total cost, so never set it and never accept "proxying is expensive" without checking it is unset. No code changed for this. (h #g166)

### `/btw`

- **Native `/btw`** (`src/side-question.ts`) uses `control_request.request.subtype: "side_question"`, answer at `control_response.response.response.response`; the gate is CLI >= 2.1.258, idle headless process only, and replies route through `dispatchSideQuestionResponse`. Never send the aside as a user envelope. `test/side-question.test.ts`. (h #g120)
  - **On the interactive transport the aside is a short-lived fork, never the TUI's own `/btw`** (`interactiveControl.askAside`, h #g203): the TUI's `/btw` answers only in an on-screen overlay that binds `c` and `f`, and nothing reaches the transcript. The fork is `ClaudeSession({ forkOf })` (`--session-id <new> --resume <main> --fork-session`) with the MAIN spawn's arguments, because the prompt cache keys on them (measured: 27,621 read, 0 written), plus `dontAsk` and no allow list so it runs no tool; its first turn reads nothing before its own prompt record (the copy keeps the parent's records), it is disposed and its transcript copy unlinked in `finally`. One aside per process still holds through `pendingProcesses`.
- **The aside question must be stripped of opencode's `<system-reminder>` blocks** (`SYSTEM_REMINDER_BLOCK`), or a short question goes out as 1,599 characters. Strip **wherever the block sits**, not by matching a whole part or anchoring at the end. Only this parse strips reminders; normal turns keep forwarding them. (h #g120)
- **`/btw` is asked early and kept in the conversation** (`src/btw-command.ts`): find the process by opencode session id, send the `side_question` **immediately**, remember the promise, and **hold the command until `client.session.status()` reports idle**. A no-process `/btw` answers with `BTW_NO_SESSION_MESSAGE` as text, not an error. `test/btw-command.test.ts`. (h #g120)
  - Three traps: the remembered answer is matched by **prefix**, not equality (dcp appends `<dcp-message-id>`); busy must come from `session.status`, not the line-listener count, which is detached while opencode runs a tool; and holding the route is fine.
- **Both lookups the hook makes are racy the instant `/btw` is typed**: doStream tags the process only after the whole spawn path, and an unregistered session is **absent from the status map and reads as idle**. `waitForAsideProcess` polls while busy and `settleSessionBusy` re-reads for `BUSY_SETTLE_MS` before concluding idle. (h #g120)
  - The settle must run **concurrently** with the request, never before it, and `answer.catch(() => undefined)` goes on immediately, or a fast failure is an unhandled rejection in opencode's process. Do not remove it as dead code.
- **The answer is written into the running turn's own reply**, falling back to the toast plus a held message. `doStream` registers an `AsideSink` per conversation (unregistered in `cleanupTurn`, its unregister deleting only its own sink) and the hook throws `BtwHandledError` on success so opencode never creates the `/btw` message. (h #g120)
  - A turn is a **run of streams**, so `deliverAsideInline` retries for `INLINE_WAIT_MAX_MS` while busy before falling back, and the block is its own text part led by `INLINE_ASIDE_MARKER`. Do not match the marker mid-part.
- **The aside's left bar is a literal `▌` the plugin emits, NOT a markdown blockquote**, and the search for a green one is closed: OpenTUI takes that colour only from theme-wide syntax scopes. `INLINE_ASIDE_MARKER` must stay the leading characters after `trimStart()`; `LEGACY_INLINE_ASIDE_MARKERS` keeps old blocks strippable. (h #g120)
- **No toast ever carries the answer**: every path that produces an answer puts it in the conversation. The **two** that stay are where nothing reaches the conversation: a bare `/btw` (`SIDE_QUESTION_USAGE`) and `BTW_TURN_TOO_LONG_MESSAGE`. `showToast` needs its receiver bound. (h #g120)
- **A receipt block goes into the turn the moment the question is sent** (`formatInlineAsideAsk`), and the answer handler **awaits** that promise first, so a receipt can never land under the answer it announces. It quotes the question **in full and untruncated**. **Updating the receipt in place is not available.** (h #g120)
- **Probing this live needs a turn that is genuinely still running**: `POST /session/:id/message?async=true` **still blocks**, so background the curl; opencode's `webfetch` times out well before 30 s; and the provider ids are `claude-code-default` / `claude-code-appical`, never a bare `claude-code`. (h #g120)

## Running The Suite

- **The `test` script forces `OPENCODE_CLAUDE_CODE_LOG_FILE=0`, and that is not tidiness**: the maintainer's shell exports `=1`, so runs appended 1,732 fixture lines and fake `plugin ready` blocks to the **live** `plugin.log`, which another session read as a broken V2 install. Tests that exercise file logging set it explicitly. (h #g116)
- **Never pipe `npm test` into `grep` inside an `&&` chain.** The pipeline exits with grep's status, not the test runner's, so a red suite reads as green and the chain continues; this carried a `npm version minor` and a tag push through five failing tests and v0.21.0 published before anyone knew. Redirect and check instead: `npm test > /tmp/run.log 2>&1; echo "EXIT=$?"`, then grep the file. (h #g117)
- **A spec must never race the 5-second probe deadline, because on a loaded machine it loses.** Measured 2026-10-01: 6 of 40 concurrent runs of `test/side-question.test.ts` lost `claude --version` to it at load 66 to 76, which refused `/btw` as "CLI too old" and left the aside empty; the same class killed two `test/skill-bridge.test.ts` specs and one in `test/startup-diagnostics.test.ts`. Resolve a probe up front and ask again when it was killed (`warmCliVersion`, `fakeCli`), never inside the window under test, and read "was this cached" off promise identity rather than a spawn count. A per-turn `AbortSignal.timeout` is a hang-stop, not a deadline: `TURN_HANG_STOP_MS`, well clear of the 5.9-second spawn measured under load. (h #g181)
- **The fake-CLI recovery tests in `test/proxy-task.test.ts` are timing-sensitive and everything they wait on derives from `START_WATCHDOG_MS`.** Under load they fail identically on master and on released tags, so run the same file at the last known-green tag before touching code. Do not raise one of the three waits on its own: the longest path lets **two** consecutive watchdog deadlines elapse. (h #g118)
