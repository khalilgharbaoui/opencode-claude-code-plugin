## Project Shape

- This is an npm package that exposes an opencode provider by wrapping the Claude Code CLI (`claude`), not the Anthropic HTTP API directly.
- Package entrypoint is `src/index.ts`; runtime provider behavior lives mostly in `src/claude-code-language-model.ts`, which now holds the `ClaudeCodeLanguageModel` class and little else. Its free-standing pieces moved out verbatim and it re-exports every symbol tests and `src/index.ts` used to import from it, so an old import path still resolves: `src/prompts.ts` (appended system prompt text and `buildAppendedSystemPrompt`), `src/auto-continue.ts` (the continue-or-stop decision), `src/ask-user-question.ts` (`AskUserQuestion` rendering and its deny message), `src/fast-mode.ts` (`reportFastModeState`), `src/call-options.ts` (session affinity, opencode agent, compaction model, `hasNewUserContent`), `src/proxy-results.ts` (reading opencode's answer back out of the next prompt), `src/control-request.ts` (`can_use_tool` allow/deny), `src/spawn-planning.ts` (proxy defs, MCP config, live tool registry, skill-bridge and plan-mode gates, the proxy server), `src/title.ts` and `src/usage.ts`. **There is one turn implementation, `doStreamForHost`, and the state its handlers shared is an object now, not a scope.** `src/turn-state.ts` holds `TurnState` and `createTurnState`, one per turn, with a comment on each field naming the invariant that owns it; `src/turn-controller.ts` holds the two watchdogs, late-result delivery, the batched drain, both tool-call finishes and the auto-continue nudge; `src/stream-parser.ts` holds the CLI line handler (`createLineHandler`) and `StreamParserContext`, the twelve prologue values it reads; `src/turn-abort.ts` holds `watchTurnAbort`, the one thing that observes this turn's abort signal, created before the prologue's first await (h #g182). What stayed in `doStreamForHost` is what also reads that prologue: the spawn block, `completeResult`, the close handler, `cleanupTurn`, the proc-error handler and the abort branch. Behaviour-preserving: no log line, stream part or session-manager call changed, and a paired live probe matched line kind for line kind. (h #g165) `doGenerate`'s duplicate copy of that parser is gone (0.29.x): `doGenerate` is `doGenerateViaStream`, which aggregates `doStream`'s parts, and the only thing that differs between the two entry points is `TurnMode`, which suppresses the account-failover dialog on a `doGenerate` turn. Measured on opencode 1.18.32: nothing there calls `doGenerate` at all, not even a title request. `test/do-generate.test.ts`. (h #g164)
- `src/message-builder.ts` owns AI-SDK prompt to Claude CLI stream-json message conversion, including `/compact` transcript rendering.
- `src/session-manager.ts` owns Claude CLI process reuse, session ids, LRU eviction, and CLI arg construction.
- `src/session-fork.ts` decides whether a new opencode session is a fork of one this provider already served, by matching conversation content rather than any host id. Pure, injected rather than importing the session manager, and only ever consulted on a turn that was about to replay. (h #g187)
- `src/conversation-gap.ts` remembers, per session key, the SHAPE of the conversation its Claude session was last asked to continue (written on every `result`), and `classifyConversationChange` answers two questions in the prologue off that one chain: which messages did that session miss while the conversation ran under another key (`missed`, h #g239), and does it still hold turns the conversation no longer has (`rewound`, h #g242)? In memory only, capped at 64, moved by `transferClaudeSession` and dropped by `deleteClaudeSessionId`; imports only `session-fork.ts` and the logger, and owns `CONVERSATION_REWOUND_MARKER`. `findMissedMessages` is the `missed` half of the classifier and is what most of the tests read.
- `src/session-resume-store.ts` keeps, across opencode restarts, which Claude session answered each session key, with the fork module's digest chain of the conversation it answered. One of the eight files the plugin writes under `$XDG_STATE_HOME`, beside `cleanup-stale.json`, `src/dispatch-choice-store.ts`'s `subagent-dispatch.json`, `src/spawn-record-store.ts`'s `session-spawns.json`, `src/account-usage.ts`'s `account-usage.json`, `src/turn-history.ts`'s `turn-history.json`, `src/turn-progress-store.ts`'s `turn-progress.json` and `src/cli-model-catalog.ts`'s `cli-models.json`. (h #g197, h #g228, h #g234, h #g244, h #g247, h #g251, h #g279) It answers two lookups off that one record: `findResumePoint` for the SAME key after a restart, and `findSiblingResumePoint` for the same conversation under another model or effort (h #g215).
- `src/cli-model-catalog.ts` is the model catalog as the installed `claude` describes it: a free background probe, the `cli-models.json` store it fills (keyed on the real binary's path, size and mtime plus its version), and the overlay every registration path reads through `effectiveModels()` instead of `defaultModels` (V1's config and `models` hooks, `v2ModelsForProvider`, and `isRegisteredModelName` for an added model). `src/models.ts` stays the source of every price and `(N×)` label. Nothing on a turn path calls it. (h #g279)

It imports nothing that logs and never throws, because the TUI bundle reads it; `src/account-sidebar.ts` is the pure line model the TUI draws from it. (h #g244)

- `src/subagent-dispatch.ts` owns the subagent dispatch form: which model, effort and account the subagents a turn is about to start should run as, and which child gets which answer. Pure apart from `ensureAccountRuntime` and the choice store, and the only thing that reads it on a turn is a gate that is null unless the operator opted in. (h #g227, h #g228)
- `src/dispatch-choice-store.ts` keeps `Same as last time` across opencode restarts: one record per opencode session id holding one `{model, effort, account}` per agent type, under `$XDG_STATE_HOME/opencode-claude-code-plugin/subagent-dispatch.json`. Same discipline as the resume store (merge-on-write, atomic rename, `0600`, an unreadable file is an empty store), and nothing but those three strings is ever written. (h #g228)
- `src/task-model.ts` owns a subagent's model named per call on opencode 2: reading the `providerID/modelID#variant` reference, completing a bare model id to the conversation's own provider (h #g255), the `accountGroups` rule it must pass, and the in-memory records that carry an explicit request from the parent's `task` call into the child's own prologue. Pure apart from the logger, imports only `account-groups.ts` and `subagent-dispatch.ts`'s `promptMatchesClaim`, and nothing reaches it unless a task names a model. (h #g254)
- `src/tui.ts` is the TUI half, a second build entry (`dist/tui.js`, `exports["./tui"]`): the sidebar's always-on `Subagents` section, the `Main Progress` line above it and the `Accounts` lines below it. `src/subagent-sidebar.ts` is everything the rows decide (rows, states, order, labels, layout, a row's spend), `src/progress-line.ts` everything the progress lines do (what is measured, the fraction, the estimate's cells and the fill memory, the linger, the status watch, the layout; h #g246, h #g247), both pure and imported by nothing that logs; `src/spawn-record-store.ts` is the one channel from the provider half for what a session runs as, `session-spawns.json`, holding what each session REALLY spawned as (`{model, effort, account, agent, at}`), written in the prologue and read by the TUI. (h #g234)
- `src/turn-history.ts` is the other channel, `turn-history.json`: one sample per served turn (`{ms, chars, effort, calls, out, failed, session, at}`, keyed `agent/model`), written at the `result` and read by the TUI, plus the counts both halves must agree on: `turnToolCalls` (h #g250), `promptChars`, `startsTurn`, `lastToolResultFailed` and `sessionTag` (h #g251). What the bar is drawn from that record is `src/turn-model.ts`, a calibrated log-normal survival model (`buildTurnModel` once per change to the store, `estimate` per line per tick, `assess` for the doctor). The output a running turn has generated so far, which only the server half can see, goes through `src/turn-progress-store.ts`'s `turn-progress.json`, written once per API call by `noteTurnOutput`. All three are pure apart from `fs`, import nothing that logs, never throw. (h #g247, h #g251)
- `src/account-groups.ts` owns the account topology: which opencode providers are this install's accounts (`accountProviderMap`, built from the configured list so it is empty on a single-account install) and which of them may see each other's conversations (`accountGroups`, off unless set). Pure, imports only `accounts.ts` and the logger, and nothing in it may ever fail a turn: every refusal leaves the guard off for the entry it refused. (h #g226)
- `src/account-transcript.ts` moves one conversation's Claude transcript between account config dirs, which is how an account switch continues a conversation instead of replaying it. Pure apart from `fs`, knows nothing about turns or accounts beyond a config dir, and every refusal is a value the caller falls back on. (h #g218)
- `src/cli-version.ts` gates optional CLI flags. Do not pass newly-added Claude CLI flags unconditionally. **A probe our own 5-second deadline killed is the one failure that is NOT cached, up to `MAX_DEADLINE_REPROBES` (2) consecutive times per probe key** (`killedByDeadline`, `forgetDeadlineKill`; the third kill is cached with one WARN, because a `claude` or wrapper that is always slower than the deadline would otherwise make every turn wait the full deadline; an answer resets the count): it describes the machine, not the binary, and caching it withheld every version-gated flag, the skill bridge and `/btw` from the whole opencode process after one busy turn. Everything else (missing binary, non-zero exit, unparseable output) stays cached, so a broken binary is still one spawn. Do not raise the deadline instead: it bounds how long a wedged `claude` holds the first turn. `test/cli-probe-cache.test.ts`. (h #g181)
- `src/read-rules.ts` resolves opencode's own `read` permission rules for the current host and translates the DENY half into Claude deny rules for the file tools the CLI runs itself (`mapReadRules`, default on). Pure apart from one `os.homedir()`, never throws (a malformed config layer reads as "nothing to map", never a failed turn), and it only ever makes a spawn stricter: an `ask` is reported rather than promoted, and a deny opencode's own `findLast` has already killed is not emitted. It owns `recordReadRuleMapping` / `snapshotReadRuleMapping`, the doctor's recorded-read seam. (h #g243)
- `src/budget-ledger.ts` is what one opencode conversation spent under `maxBudgetUsd`: per session (the affinity) its own turns plus every descendant's, children linked by `fetchSessionParentId`, read off the CLI's `total_cost_usd` as a DELTA per Claude session id because a headless total is cumulative (`costDelta`). In memory, capped (256 sessions, 512 Claude ids), pure apart from the logger, and nothing reaches it unless the option is set (`resolveTurnBudget` returns null). It owns `BUDGET_MARKER`, both notes, the option resolvers and `snapshotBudgets`, the doctor's read. (h #g245)
- `src/plan-usage.ts` runs the CLI's own free `/cost` command for `/claude-code-doctor usage`, and is the only place the plugin invokes a CLI slash command. Nothing on a turn path may import it. (h #g167)
- `src/stale-build.ts` answers one question nothing else in opencode can: is the build this process is RUNNING still the build on disk? It records the loaded version, entry path, mtime and size at module load, and a throttled check re-reads them. Pure apart from `fs`, injectable through `createStaleBuildWatch`, and the only module that may call `pluginVersion()` for a comparison. (h #g192)
- `src/plugin-copies.ts` decides which copy of the plugin runs a turn on opencode 2, so a rebuild applies without a restart (h #g269). Every copy registers under one versioned `Symbol.for` key, and the provider the V2 `sdk` hook hands opencode asks `routeTurn` on every `doStream` and `doGenerate`. The entry shape (`holds`, `quiet`, `release`, `modelFor`) is a contract between builds, because the FIRST copy's routing code runs for the life of the process: it may only grow, and a breaking change takes a new key.
- `src/tui-log-sink.ts` is the only thing that knows opencode's `app.log` and `tui.showToast` routes. It builds the `LogSink` `src/logger.ts` uses when a full-screen TUI owns the terminal, and is imported from the V1 entry only. Pure apart from those two calls, and it must never import anything that logs. (h #g193)
- `src/plugin-notice.ts` is how the plugin's warnings reach the screen on opencode 2, where its server half runs in a process with a piped stderr and no toast route: an RPC definition (plain JSON Schema, which `Rpc.PortableDefinition` accepts, so no schema library at runtime) registered on `ctx.rpc` in every V2 `setup`, whose events travel on the bus as `rpc.opencode-claude-code-plugin.notice` and which `setupV2` in `src/tui.ts` raises through `ui.toast.show`, once per notice id. Scoped to one opencode instance by construction, which a shared file under `$XDG_STATE_HOME` would not be. Imports nothing, never throws or logs, because the TUI bundle reads it. (h #g253)
- `src/diagnostic-bundle.ts` is the allowlist redactor behind `/claude-code-doctor bundle`; `src/log-messages.ts` is its generated set of plugin-authored NOTICE/WARN/ERROR message literals, and `src/log-message-scan.ts` is the extractor that produces it. **`log-message-scan.ts` reads `src/` off disk, so nothing on a turn path may import it**: only `scripts/generate-log-messages.ts` and `test/diagnostic-bundle.test.ts` do. (h #g183)

## Release Workflow

- Never run `npm publish` manually. Tag push triggers `.github/workflows/publish.yml`, which publishes to npm.
- Publishing uses npm **trusted publishing (OIDC)**, not a token (since v0.6.2): `id-token: write`, npm >= 11.5.1, `npm publish --access public` with **no `NODE_AUTH_TOKEN`**. The trusted publisher must match the repo and workflow filename `publish.yml`; the legacy `NPM_TOKEN` secret is unused. If a publish fails on auth, check that config, not a token. (h #g17)
- Release flow: commit code/docs, then `npm version patch -m "v%s"` (or minor/major), then `git push origin master --follow-tags`, then, once the publish is verified, the GitHub Release (next rule). Prior tag messages are `v0.x.y`, keep that style, and confirm with `gh run list --limit 3`. **The `-m "v%s"` is not optional**: npm's default message is the bare `%s`, which is how v0.61.0's commit and tag message became `0.61.0` (as 0.11.x to 0.14.x had), noticed only after the push (h #g260).
- **Verify a publish from the `Publish package` step's own tail (`+ <pkg>@<version>`) and cross-check the version document's `shasum` against its `npm notice shasum:` line; the version document can lag the publish by several minutes (about seven on 2026-10-01), so poll for ten before concluding anything. Never judge a release by the package document, `npm view` or an install from the maintainer's Mac**, where Aikido's minimum-package-age filter hides fresh versions. Read Aikido's event log before calling anything a registry fault. A real auth failure fails the step with a 404 on the PUT. (h #g21)
- **Every release gets a GitHub Release, created after the publish is verified**: `gh release create vX.Y.Z --title vX.Y.Z --notes "<what changed, the PR, the history entry>"`, short notes, no hype, the same tone as a commit message. The maintainer asked for it on 2026-10-18 ("tag the release also on github next time"), after v0.57.0 went out with only the tag and the npm publish. It was not the lone omission, and the check that said so read a list as a diff: `gh release list --limit 100` spanned v0.4.14 to v0.56.0, but that span held 115 tags and 98 Releases. **Check parity by diffing the full sets**: `git ls-remote --tags origin` against `gh release list --limit 1000 --json tagName`, and npm by each tag's version document (h #g21). That diff found 17 tags with no Release (v0.9.3 to v0.13.1, v0.21.0, v0.27.1, v0.27.2, v0.41.0 to v0.42.3), all on npm, and the maintainer had them backfilled, so since 2026-10-18 every tag has exactly one Release. (h #g22)'s "lapsed after v0.9.2" was right about where the gaps began; this rule replaces its "optional". Three tags never reached npm and their Releases say so (v0.1.3, no publish run; v0.6.0 and v0.6.1, the expired token before trusted publishing, h #g17), npm's first publish, 0.1.0, has no tag, and every tag from v0.6.2 on is on npm. **Create a backfill with `--latest=false`**, because GitHub's Latest badge follows creation time: the backfilled v0.57.0 took it from v0.57.1 until `gh release edit v0.57.1 --latest` gave it back. An older tag is backfilled only when asked. (h #g22, #g249, #g252)
- A freshly published version will NOT appear in a local opencode until its cache entry is removed plus a full relaunch; a plain restart never re-resolves `@latest`. opencode 1.x keeps it at `~/.cache/opencode/packages/@khalilgharbaoui/opencode-claude-code-plugin@latest`, opencode 2.x at `~/.cache/opencode/npm/@khalilgharbaoui/opencode-claude-code-plugin@latest`, and on 2.1.4 neither `opencode plugin check`/`update` nor `opencode plugin list` sees this plugin (measured 2026-10-31 on a clean install, Claude Code 2.1.314). (h #g23)
- Do not add a Claude co-author trailer to commits.
- Keep the `docs/` pages updated when adding public options, env vars, required CLI versions, or behavior users can observe; `README.md` is the landing page and changes only when its own copy stops being true. See the docs rule under Commands. (h #g188)

## High-Signal Runtime Gotchas

### Aborts, deadlines and process lifetime

- **The run-state read that decides whether an abort at a tool boundary is real must ask for the session's own directory.** opencode keeps one status map per workspace directory and the plugin's client is scoped to whichever directory loaded it last, so asked without a directory a session running in any other workspace is absent from the map and reads `idle`: every abort at a tool boundary then rejected the parked call (`Provider stream was aborted while opencode was running its proxy tool calls`) and interrupted the CLI, which the model reported as the user interrupting it. Measured 2026-10-05 on 1.18.32: five sessions busy, each in its own workspace, the unscoped map empty and each per-directory map showing them busy; 111 such rejections in two and a half days of one machine's CLI transcripts, hitting long tool calls (VM ssh) in seats that run in their own workspace. `fetchSessionRunState(sessionID, directory?)` looks the directory up with `fetchSessionDirectory` when not given one, `settleSessionRunState` once per window, and the release now logs the state it read. `test/runtime-status-sessions.test.ts`, `test/process-lifecycle.test.ts`. **opencode 2 has no status route at all, and there `fetchSessionRunState` answers from its event stream** (`noteSessionRunEvent`, fed by `followSessionEvents` in `src/v2.ts`; h #g253): `session.execution.started` is busy, `succeeded`, `failed` and `interrupted` are idle, measured on 2.0.22 and 2.0.31 to agree with `GET /api/session/active` through a 15-second permission hold and an 8-second tool run. `session.status` and `session.idle` are in its generated types and were never emitted; they are read anyway. A session not seen since the feed opened is `unknown`, which every caller already treats as "do not act", and closing ANY feed forgets everything, because a feed that ended can have missed the event that would have ended a busy session, and a stale `busy` would keep a dead proxy call alive. opencode 1 never feeds the map, and its client's route wins whenever there is one. `test/v2-session-events.test.ts`.
- **A tool-result turn resolves the parked proxy calls and writes no user envelope, so user messages the host promoted beside those results must be forwarded or the CLI never sees them.** opencode records a background-PTY notice, a mail-watch notice or a steered prompt as delivered when it promotes it at the step boundary, and the next prompt carries it after the tool result; the matched-results branch returned without writing it (measured 2026-10-05 against a live server: the Claude CLI transcript held none of six notices recorded by opencode, and held all six as `queued_command` attachments once forwarded). `getTrailingUserMessages` returns the plain user messages after the last assistant message, and `ActiveProcess.forwardedUserMessages` (assistant index and count) stops a later tool-result turn for the same boundary sending them twice. Judge delivery by the CLI transcript, not opencode's history: a mid-turn stdin message appears there as `queue-operation` plus a `queued_command` attachment, not as a `user` row. On the interactive transport a stdin write is a new TUI turn that would supersede the one parked in the proxy call (h #g204), so the message is typed into that turn's own input queue instead (`interactiveControl.queueInput`, h #g206): measured on 2.1.288, text submitted while a tool call runs is recorded as `queue-operation` enqueue/remove plus a `queued_command` attachment and answered in the same turn, which ends once. Only while the TUI turn runs, never into a parked plan dialog, confirmed by the enqueue record before the call is resolved. Live, both majors and both transports, A/B against v0.42.0 (which dropped it). `test/forward-user-content.test.ts`, `test/interactive-pty.test.ts`.
- **An abort at a proxy tool boundary is usually opencode, not the operator**: 1.18.32 aborts every step ending in tool calls, and `AbortSignal.reason` is identical either way. Only a positive `busy` from `settleSessionRunState` keeps the pending calls; `unknown` releases. `test/process-lifecycle.test.ts`. (h #g26)
- **An abort that lands while a turn is being PREPARED must stop it, and the only thing that can see it is a watch created before the prologue's first await** (`watchTurnAbort`, `src/turn-abort.ts`): `addEventListener("abort")` on a signal that already aborted never fires, so the stream's own handler, which cannot exist until the prologue has finished, missed every stop in that window and the turn spawned, wrote and billed anyway (measured: a turn alive at 5,874 ms against a 5,000 ms signal). ### Scratch files on disk

- **The scratch dir is `0700` and a pre-existing symlink, non-directory or foreign-owned path at the pid name is refused** for a fresh `mkdtempSync` one, re-checked every `pluginTmpDir()` call. (h #g158)
- **Nothing spawns `claude` with `shell: true` any more, and `src/windows-spawn.ts` is the one place that knows why.** `planClaudeSpawn` returns the command untouched off Windows and is the only thing any spawn site calls; on `win32` it resolves the command against PATH and PATHEXT itself (deliberately **not** the current directory, which `CreateProcess` would search), runs a `.exe` with `shell: false`, and sends a `.cmd`/`.bat` through `cmd.exe /d /s /c` with the command path quoted and each argument through `quoteBatchArgument`, with `windowsVerbatimArguments` so Node does not re-quote it. The old `shell: win32` passed the whole command line to cmd unquoted, so `& | > < ^ (` injected and a space or a quote broke the argument list; it was there because `CreateProcess` cannot run the `claude.cmd` npm shim at all, which is why dropping the shell needed the resolver first. **Caret escaping is NOT the answer here and the Windows job proved it**: a batch shim forwards `%*`, so cmd parses the line twice, the carets are spent on the first pass, and `"x\" & echo pwned > pwned.txt & "` created the file on `windows-latest` (CVE-2024-27980's shape; cross-spawn emits exactly that escaping). What survives both passes is quoting with DOUBLED quotes (`"` wrapper, `""` for an embedded quote, backslashes before one doubled), which keeps cmd's quote state balanced on both passes so no metacharacter is ever outside quotes, and which `CommandLineToArgvW` reads back exactly. That is what Rust adopted for `.bat` after the same CVE. Never emit a caret from here: inside the quoting it arrives as a literal caret in the value. A newline throws, because cmd ends the command line at one and the alternative is silent truncation. **`%` is the one hole that stays**: cmd expands `%NAME%` before anything else is considered, `^%` is unavailable for the reason above and `%%` is batch-file-only, so a `%` argument may arrive with a variable substituted into it. It cannot inject, because the substitution lands inside quotes cmd has already opened. **The escaper is unit-tested on every platform and PROVEN on `windows-latest`**, where `.github/workflows/ci-windows.yml` spawns a real `.cmd` shim that echoes its argv back; the skipped files are `.github/windows-skipped-tests.txt`, one reason per group, and the job fails on a stale entry. Do not add a dependency for this (cross-spawn's algorithm is ~60 lines) and do not change the escaper without reading the CI job's output. One Windows gap is open on purpose: the interactive PTY transport refuses a `.cmd` rather than running one, because `cmd.exe /c` would own the terminal the TUI draws on. `test/windows-spawn.test.ts`. (h #g158, #g217)
- **`accounts` works on Windows by generating NOTHING, and a `.cmd` twin of the wrapper is the wrong fix.** The bash wrapper does two things, export the account's `CLAUDE_CONFIG_DIR` and take the `@<account>` marker off `--model`; a `.cmd` would have to forward the rest with `%*` (a THIRD cmd parse on top of the two `quoteBatchArgument` is proven against) and, worse, re-emit the one argument it rewrites, which in batch means reading it back through `%1`/`shift` and re-quoting it in a language whose escaping was measured injectable (h #g217). So on `win32` `ensureAccountRuntime` returns `{cliPath: baseCliPath, configDir, accountInProcess: true}` and the two jobs are done in process: `claudeSpawnEnv({configDir})` sets the variable (threaded through `spawnClaudeProcess`, carried by `respawnActiveProcess` off `ActiveProcess.configDir`, and given to the doctor's `/cost` spawn), and `doStream` strips the marker where it already computes the spawn model, `parseModelId(stripAccountSuffix(...))`. **Both are gated on `accountInProcess` and nothing else, so POSIX is byte-identical and `test/account-wrapper.test.ts` passes unmodified**; `ensureAccountRuntime` takes an injected `platform` so the win32 plan is testable on a Mac. **The account identity moved with it**: every Windows account runs the same binary, so the failover prologue's `cliPath` comparison could never fire there and a switch would have kept the wrong config dir. `processBelongsToAnotherAccount` owns both call sites, `configDir` is recorded only where the plugin sets it itself, and on POSIX that second term is always absent, which is what makes it the old condition exactly. **`ensureSharedCapabilities` is per item now**: a directory is a `junction` (no privilege), a FILE is symlink -> hard link -> copy-with-a-WARN (a file symlink needs Developer Mode), and one item failing must never cost the others theirs, which is what it did before. `test/account-windows.test.ts`. (h #g221)

## Running The Suite

- **The `test` script also sets `OPENCODE_CLAUDE_CODE_MODEL_PROBE=0`** (h #g279): five files drive a config hook or a V2 setup (`index-hooks`, `plugin-copies`, `plugin-notice`, `proxy-task`, `v2-entrypoint`), and each would otherwise probe `claude` in the background. A focused run of one of them outside `npm test` should set it too; the probe is free, but it writes `cli-models.json` wherever `XDG_STATE_HOME` points.
- **The `test` script forces `OPENCODE_CLAUDE_CODE_LOG_FILE=0`, and that is not tidiness**: the maintainer's shell exports `=1`, so runs appended 1,732 fixture lines and fake `plugin ready` blocks to the **live** `plugin.log`, which another session read as a broken V2 install. Tests that exercise file logging set it explicitly. (h #g116)
- **Never pipe `npm test` into `grep` inside an `&&` chain.** The pipeline exits with grep's status, not the test runner's, so a red suite reads as green and the chain continues; this carried a `npm version minor` and a tag push through five failing tests and v0.21.0 published before anyone knew. Redirect and check instead: `npm test > /tmp/run.log 2>&1; echo "EXIT=$?"`, then grep the file. (h #g117)
- **A spec must never race the 5-second probe deadline, because on a loaded machine it loses.** Measured 2026-10-01: 6 of 40 concurrent runs of `test/side-question.test.ts` lost `claude --version` to it at load 66 to 76, which refused `/btw` as "CLI too old" and left the aside empty; the same class killed two `test/skill-bridge.test.ts` specs and one in `test/startup-diagnostics.test.ts`. Resolve a probe up front and ask again when it was killed (`warmCliVersion`, `fakeCli`), never inside the window under test, and read "was this cached" off promise identity rather than a spawn count. A per-turn `AbortSignal.timeout` is a hang-stop, not a deadline: `TURN_HANG_STOP_MS`, well clear of the 5.9-second spawn measured under load. (h #g181)
- **The fake-CLI recovery tests in `test/proxy-task.test.ts` are timing-sensitive and everything they wait on derives from `START_WATCHDOG_MS`.** Under load they fail identically on master and on released tags, so run the same file at the last known-green tag before touching code. Do not raise one of the three waits on its own: the longest path lets **two** consecutive watchdog deadlines elapse. (h #g118)
- **A fixture that repoints `HOME` must not put its scratch tree under the REAL home, because `skillRoots`' walk-up guard is `current !== os.homedir()` and `os.homedir()` follows `$HOME`.** opencode's sandbox sets `TMPDIR` inside the maintainer's home, so `os.tmpdir()` sat under it and the walk-up read `~/.claude/skills` and `~/.agents/skills` as ordinary project ancestors: `test/skill-bridge.test.ts` discovered 114 skills instead of its own and failed 3 specs on that Mac while CI passed. Not a product bug (a real workspace reaches its own home with `current === homeDir`, and an ancestor that is not the home dir IS a root opencode reads), so `scratchRoot()` takes the first candidate with no skill root above it and throws naming every dirty one when none is clean, and each fixture asserts `skillRoots(cwd)` holds nothing outside its base. **The 101 skills that did NOT reach an assertion are the lesson**: they came from `~/.claude/skills`, which the native scan reached the same way and `dropNativelyLoadedSkills` then skipped, so the prefix-filtered specs kept passing while measuring the operator's machine. A leaked root changes what a filtered spec proves rather than failing it. (h #g263)
